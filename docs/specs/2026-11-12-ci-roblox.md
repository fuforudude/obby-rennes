# CI GitHub : contrôles des PR et publication sur Roblox

Statut : en cours (code relu et prêt ; reste la PR et le premier essai sur GitHub)
Date : 2026-11-12

## Besoin
Aujourd'hui, chaque modification doit être republiée à la main depuis Studio, sans trace de ce qui est en ligne. L'étudiant veut que GitHub contrôle chaque PR, publie tout seul chaque version fusionnée sur une expérience de test, et ne mette en production qu'après son approbation.

## Périmètre
- Dedans :
  - un workflow de contrôle sur chaque PR et sur chaque push de `main` ;
  - la publication automatique sur l'expérience de test après chaque fusion sur `main` ;
  - la publication en production derrière une approbation manuelle (environnement GitHub protégé) ;
  - le lanceur des tests Lune et le vérificateur de sauts rendus utilisables en CI (dans le dépôt, pas dans un dossier temporaire) ;
  - un script de publication dans le dépôt, sans dépendre du plugin installé sur le PC ;
  - la trace de chaque publication (résumé du workflow : version Roblox, commit).
- Hors périmètre :
  - les tests TestEZ exécutés dans le cloud Roblox ;
  - la revue, la correction et la fusion automatiques par Claude (pas de jeton Claude chez GitHub) ;
  - la création des expériences et de la clé Open Cloud, et les réglages GitHub : faits par l'étudiant (liste plus bas).

## Critères d'acceptation
- [ ] Une PR vers `main` déclenche le check `verifier`, qui échoue si un fichier est mal formaté (StyLua), si Selene trouve une erreur, si la construction Rojo échoue, si un test des règles échoue ou si un checkpoint devient inatteignable.
- [ ] Le check `verifier` n'utilise aucun secret : il passe sur une PR sans clé Roblox.
- [ ] Après une fusion sur `main` avec `verifier` vert, le job `publier-test` construit `jeu.rbxl` et le publie sur l'expérience de test ; le numéro de version renvoyé par Roblox et le commit apparaissent dans le résumé du workflow.
- [ ] Le job `publier-prod` ne démarre qu'après `publier-test` réussi **et** l'approbation manuelle de l'étudiant dans l'environnement GitHub `production` ; il publie le même fichier `jeu.rbxl` que la version de test.
- [ ] Sans approbation, rien n'est publié en production.
- [ ] La clé n'apparaît jamais dans le dépôt ni dans les journaux (secret `ROBLOX_API_KEY` de GitHub, masqué).
- [ ] Les identifiants des deux expériences sont lus dans `.claude/roblox.json` ; s'ils valent 0, le job de publication s'arrête avec un message clair.
- [ ] En local, `lune run outils/tests/lancer-specs.luau` et `lune run outils/monde/verifier-sauts.luau` donnent le même résultat que dans la CI.

## Décisions techniques
Prises par l'étudiant le 2026-11-12.
| Question | Options envisagées | Choix | Raison |
|---|---|---|---|
| Où publier automatiquement après chaque fusion | Expérience de test séparée ; directement sur la vraie | Expérience de test séparée | Un bug ne touche jamais les joueurs |
| Comment déclencher la production | Bouton d'approbation (environnement protégé) ; tag de version ; toujours à la main | Bouton d'approbation | Traçable, un clic après avoir essayé la version de test |
| Contrôles des PR | Vérif + tests Lune + sauts ; en plus tests TestEZ dans le cloud Roblox | Vérif + tests Lune + sauts | Rapide, sans clé Roblox pour les PR |
| Revue et correction par Claude dans la CI | Seulement contrôles + publication ; tout le circuit des agents | Seulement contrôles + publication | Commencer simple, aucun jeton Claude chez GitHub |
| Clés Open Cloud (après revue : clé de dépôt trop exposée, environnement créé sans protection) | Deux clés, une par expérience, chacune dans les secrets de son environnement GitHub (`test`, `production`, branche `main` seulement) ; une seule clé dans les deux environnements | Deux clés | Si la clé de test fuit, la vraie expérience ne risque rien ; un environnement créé par accident n'a pas de clé |
| Carte publiée = carte vérifiée (après revue) | Régénérer la carte avant de construire ; exiger un .rbxm commité à jour | Régénérer avant de construire | On publie toujours ce qui a été vérifié, sans dépendre d'un oubli de commit |
| Gouttière du Parlement (après revue) | L'élargir jusqu'à la première lucarne ; garder 3,5 studs | L'élargir | Plus de piège sur un saut haut pour les jeunes joueurs, sans raccourci |
| Alerte « mortel trop proche » (après revue) | Version minimale (départ et arrivée, hauteur occupée) ; volume complet du saut | Version minimale | Couvre les cas évidents sans fausses alertes |

## Tâches
1. **Outillage dans le dépôt** : `outils/tests/lancer-specs.luau` (mini TestEZ pour Lune, faux `game`, lance `tests/partage/*.spec.luau`, code de sortie 1 en cas d'échec) ; `outils/monde/verifier-sauts.luau` renvoie un code de sortie 1 si un checkpoint est inatteignable ou si une pièce mortelle est à portée d'un saut ; `outils/publier.sh` (ou `.mjs`) publie un `.rbxl` par l'API Open Cloud (`POST /universes/v1/{universeId}/places/{placeId}/versions?versionType=Published`, en-tête `x-api-key`), lit les identifiants dans `.claude/roblox.json` selon la cible `test` ou `prod`, et affiche le numéro de version. Durée estimée : 30 min
2. **Workflows** : `.github/workflows/verifier.yml` (PR et push de `main` : installation des outils par Rokit, `stylua --check src tests outils`, `selene src`, `rojo build`, `wally install`, tests Lune, génération de la carte et vérification des sauts) et `.github/workflows/publier.yml` (push de `main` : construction, `publier-test`, puis `publier-prod` dans l'environnement `production`). Durée estimée : 30 min, en parallèle de la tâche 1 (elle appelle ses scripts par leur chemin).
3. **Documentation** : section « CI et publication » dans `CLAUDE.md` et `docs/publications.md` (comment approuver une mise en production, où lire les versions). Durée estimée : 10 min, faite avec la tâche 2.

Durée estimée du jalon : 1 h 15 (tâches 1 et 2 en parallèle : 30 min ; revue : 15 min ; corrections et PR d'essai : 30 min), hors réglages à faire par l'étudiant.

## Ce que l'étudiant fait lui-même (Claude ne peut pas)
1. Créer la branche `main` sur GitHub depuis `agents/premier-jalon`, et la mettre en branche par défaut.
2. Créer une 2e expérience **privée** « Obby Rennes (test) » et y publier une première fois le jeu depuis Studio.
3. Relever l'**Universe ID** et le **Place ID** des deux expériences (Creator Hub → ⋯ → Copier).
4. Créer la clé Open Cloud (create.roblox.com → Open Cloud → API Keys), droit `universe-places` en écriture sur les deux expériences, et la mettre dans les secrets GitHub du dépôt sous le nom `ROBLOX_API_KEY`.
5. Créer l'environnement GitHub `production` (Settings → Environments) avec lui-même comme *Required reviewer*.
6. Protéger `main` (Settings → Branches) : PR obligatoire, check `verifier` obligatoire.
